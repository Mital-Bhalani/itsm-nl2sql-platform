# Diagnose eval failures

Explain **why** NL2SQL eval questions failed and **which semantic-catalog entry** to fix. This
skill is diagnostic only: read, classify, recommend. Do not edit files, rebuild the catalog or
commit unless the user explicitly asks after seeing the report.

## Inputs

1. **Failed questions.** In order of preference:
   - Run `python -B evals/run_evals.py --json` and take every result whose `status` is not
     `pass`. Each result has `id`, `question`, `status`, `generated_sql`, `expected_rows`,
     `actual_rows`, `error`.
   - If the harness does not exist or cannot run, use failures the user pasted. If there are
     none, stop and say what is needed. Never invent failures.
2. **Reference SQL** for each failed question, from the eval set in `evals/`.
3. **The catalog**, read-only from the project database (here `db/tickets.sqlite`):
   `meta_tables`, `meta_columns`, `meta_metrics`, `meta_glossary`, `meta_joins`. Open SQLite
   read-only (`file:...?mode=ro`, `uri=True`) and run Python with `-B`.
4. **Term lookup.** If the project has a lookup helper, use it the way the agent does (here
   `find_term(conn, phrase)` in `semantics/build_catalog.py`, which also handles plurals).

## Procedure

For each failed question:

1. **Diff the SQL.** Compare `generated_sql` with the reference SQL clause by clause: SELECT
   expressions and aggregates, FROM and JOINs, WHERE, GROUP BY, ORDER BY and LIMIT. Note every
   difference, then compare `expected_rows` with `actual_rows` to confirm which one changed
   the result.
2. **Trace each question phrase to the catalog.** Split the question into business phrases
   ("breached", "teams", "last month", "sev1"). Look each one up. Record: resolved to the right
   entry, resolved to the wrong entry, resolved to an ambiguous entry, resolved to an
   unanswerable concept, or not found.
3. **Classify the root cause** using the first rule that fits:

   | Root cause | Signal in the SQL diff | Catalog entry to inspect |
   |---|---|---|
   | **Wrong metric** | Aggregate or formula differs from the metric definition: AVG instead of SUM, count instead of rate, missing the metric's fixed filter (e.g. only Resolved/Closed), wrong time column | `meta_metrics` row: `sql_expression`, `filters`, `required_joins`, `time_column`, `unit`, `notes`; the `meta_glossary` metric term pointing to it (`metric_name`) |
   | **Wrong join** | Missing, extra or different JOIN; join on the wrong key; row fan-out (inflated counts, e.g. joining users to incidents through a team) | `meta_joins` row for that path (left/right table and column, cardinality, notes); `meta_columns.references_to`; `meta_metrics.required_joins` |
   | **Wrong filter** | WHERE differs: wrong status list, wrong priority value, wrong date window, filter on the wrong column | `meta_glossary` value/time term `sql_hint`; `meta_columns` `allowed_values` and `description` of the filtered column |
   | **Misunderstood term** | A question phrase was not found, matched the wrong term, used an ambiguous term without asking, or an unanswerable concept was answered anyway | `meta_glossary` `term`, `synonyms`, `is_ambiguous`/`ambiguity_note`, `is_answerable`; `meta_columns.synonyms` |
   | **Not a catalog problem** | `unsafe` (non-SELECT), SQL syntax error unrelated to catalog content, harness bug, or an API error such as a missing key or exhausted quota | Report separately; do not blame the catalog |

   If a question has several causes, list the one that changed the result first.
4. **Name the exact entry.** Identify it by table and key, for example
   `meta_glossary[term='last month'].sql_hint`, `meta_metrics[metric_name='sla_breach_rate'].filters`,
   `meta_columns[incidents.status].description`, or "missing row:
   `meta_joins[incidents.assignment_group_id -> assignment_groups.id]`". Say whether it is
   **missing**, **wrong**, or **ambiguous and unflagged**, and quote its current value.
5. **Recommend a fix** for each entry: the new value (description, synonym, definition,
   sql_hint or join row) and where it lives in the source. In this repo every catalog entry is
   generated by `semantics/build_catalog.py`:
   - column descriptions → `COLUMN_DRAFTS`; column synonyms → `COLUMN_SYNONYMS`
   - priority wording → `PRIORITY_LEVELS` only (it generates descriptions, synonyms and terms)
   - metrics → `METRICS`; glossary terms → `GLOSSARY`
   - `meta_tables` and `meta_joins` rows are not generated yet: recommend adding them there
   Prefer a catalog fix over changing the agent. If the right meaning is a business decision,
   recommend flagging it as ambiguous instead of guessing.

## Output

1. One line: failed questions analysed, and the count per root cause.
2. One section per root-cause group:
   - the questions in the group (id and text)
   - a table: `catalog entry | problem (missing / wrong / ambiguous) | current value | recommended fix | source location`
3. A "Not a catalog problem" section, if any.
4. **Suggested order of fixes**: the fix that repairs the most failing questions first.
5. Next steps: change one entry, show the before/after diff, then roll it out; rebuild with
   `python -B semantics/build_catalog.py` (its self-checks must pass); re-run `/build-catalog`
   and `/run-evals` to confirm accuracy improved.

## Rules

- Read-only. No edits, rebuilds, commits or pushes without the user's go-ahead.
- Base every claim on the SQL diff, the rows or the catalog contents. If the cause cannot be
  determined, say so rather than guessing.
- Never print secrets from `.env`.
